# 禁止事项（防回归）

本文件集中记录不可违反的规则。动手前先读；如已违反，必须回退，而不是叠加新改动。

新增或修改任何规范，一律写入本文件。

## 1. 前端改动：禁止浏览器验证、禁止单元测试

**范围**：HTML / CSS / JS、静态页、样式、交互等前端改动。

**规则**：改动完成后——

- **禁止**打开浏览器、使用浏览器工具、截图或端到端点击来验收。
- **禁止**为此编写单元测试、测试文件或测试框架。
- 改完即止；是否正确由用户自行查看。

**例外**：仅当用户在**当前这条消息里明确授权**时，方可解除上述限制。历史对话或通用规则中的「改 UI 要开浏览器验证」「逻辑要留测试」**不能**覆盖本条。

**未授权时不得**：启动本地预览后点页面、调用浏览器 MCP、补 `*.test.js` 或自检脚本「顺便验一下」。

## 2. 面向公众的文档只写网站简介

**范围**：`README.md` 以及仓库中任何面向公众、可被外部看到的说明性文件。

**必须**：只做网站的简单介绍——这是什么站点、包含哪些内容、服务器基本信息、免责声明等，供不了解本仓库的人快速了解。

**禁止写入**（不得出现在公开文档中）：

- 部署方法、托管平台的配置步骤（如 Cloudflare Pages）
- 维护方法、更新流程、内部约定
- 技术栈、目录结构、构建方式、本地预览等实现细节
- 任何不应向公众展示的内部信息

**原因**：README 面向公众。部署与维护属于内部信息，不应公开展示。

**违规处理**：立即回退到违规前的状态；若已推送，需从分支历史中移除（必要时 `push --force-with-lease`），而不是仅追加一个修正提交。

## 3. 未经明确许可禁止 commit / push

**规则**：没有用户**在当前这条消息里的明确许可**，禁止执行 `git commit`、`git push`，以及任何改写远程历史的操作。

**必须**：改动完成后停在「工作区已修改」状态，等待用户明确指示再提交或推送。

**不算许可的情况**：此前对话中的授权、「应该提交了吧」之类的推测、以及任务本身隐含需要提交，均不构成许可。只有明确说出「commit / 提交 / push / 推送」等才算。

**违规处理**：若在未获许可的情况下已提交或推送，立即回退并从分支历史中移除（必要时 `push --force-with-lease`）。

## 4. commit / push 前必须完成安全排查

**规则**：在执行 `git commit` / `git push` 之前，必须先对**本次将进入提交的**工作区改动做一次安全排查，确认无敏感信息与风险后，才能提交或推送。用户明确要求 commit / push，**不豁免**本排查。

**排查范围（至少包括）**：

- 密钥与凭证：`api key` / `token` / `secret` / `password` / 私钥，以及 `AKIA` / `ghp_` / `sk-` / `xox*` 等特征串
- 个人信息：本机绝对路径（`C:\`、`Users\`、`AppData` 等）、个人邮箱、账号、用户名
- 忽略规则：确认 `.gitignore` 覆盖的文件（如 `tmp-images/`）未被误加入
- 提交身份：作者邮箱是否为预期（避免公开真实邮箱）
- 公开文档：面向前台的文件是否符合本文件第 2 条（只写网站简介）
- 二进制资源：图片 / 字体等是否含意外元数据

**跨会话 / 跨窗口情形**：若无法确信当前工作区的改动**已在本会话内被完整排查**（例如改动可能来自其他窗口、其他 agent 或用户手动操作），**必须先询问用户是否已在别处完成安全排查**；得到确认前不得提交或推送。

**结论要求**：排查后应向用户给出明确结论（通过 / 发现问题），再进行提交或推送。

**违规处理**：若未排查即提交或推送，立即回退并从分支历史中移除（必要时 `push --force-with-lease`）。
